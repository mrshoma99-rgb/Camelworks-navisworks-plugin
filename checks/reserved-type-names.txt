# Type names CamelWorks.Core must not use for a public type.
#
# CamelWorks.Core compiles on Linux with no Autodesk or WPF reference in sight — that is the
# whole point of the seam. The consequence is that a Core type sharing its name with something
# in System.Windows or Autodesk.Navisworks.Api compiles perfectly here and then fails four
# Windows jobs at once with CS0104, because CamelWorks.UI imports both namespaces and the bare
# name is suddenly ambiguous. It cost a full CI cycle to learn that PropertyPath is a WPF type,
# so the lesson is written down here instead of being learned twice.
#
# ADVISORY, NOT AUTHORITATIVE. The Windows jobs are the authority; this list only catches the
# mistake a minute earlier and on the machine that made it. The WPF half is hand-written from
# the namespaces CamelWorks.UI imports (System.Windows, .Controls, .Media); the Autodesk half is
# every public type directly in Autodesk.Navisworks.Api and .Plugins, read out of the reference
# assemblies; the base-class-library half is at the bottom and is explained there. Adding a name
# here is free. Removing one needs a reason.
#

#
# System, System.Globalization, System.IO, System.Text and System.Linq are imported by nearly
# every file in the host assemblies — System.Globalization in particular, because every number and
# date in this product is formatted with CultureInfo.InvariantCulture. A Core type sharing a name
# with one of them compiles on this machine and is CS0104 on all four Windows jobs, which is the
# same failure shape as the WPF half above and arrives the same ten minutes too late.
#
# Only names that are plausible as a domain type are listed. Nobody is going to call a Core type
# StreamReader; somebody very nearly called one CompareOptions.
